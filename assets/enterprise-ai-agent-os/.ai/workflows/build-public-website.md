# Build Public Website Workflow

Use this workflow for a new or materially changed public website, landing page, documentation site, publisher, ecommerce surface, local-business site, or SaaS marketing surface.

1. Run the Repository Intelligence Gate.
2. Complete `.ai/templates/design-brief.md`: identify site type, audiences, user goals, brand assets, approved references, locales, primary entities, public page types, content hierarchy, rendering model, hosting surface, and intentionally private routes.
3. Use `design-taste-website` in `direction` mode. Establish the design read, contextual layout/motion/density controls, design system, responsive composition, state inventory, accessibility, performance, content, and asset-rights boundaries.
4. When material motion is proposed, use `animation-design-engineering` in `opportunities` and then `direction` mode. Decide what should remain static, then define purpose, vocabulary, tokens, timing, spatial behavior, reduced-motion alternatives, interruptibility, gesture, lifecycle, performance, compatibility, and evidence.
5. Use `seo-geo-website` in `plan` mode. Define the discovery contract for every page type: canonical behavior, indexability, robots policy, locale behavior, sitemap inclusion, internal-link expectations, and structured-data eligibility.
6. Define verified content inputs. Mark missing business facts, authorship, credentials, products, prices, availability, reviews, ratings, locations, sources, testimonials, customer logos, awards, and asset rights as unknown; never invent them.
7. Reconcile visual composition and animation with information hierarchy and SEO/GEO content requirements. Do not hide or remove necessary product meaning merely to satisfy an aesthetic or motion preference.
8. Plan raw/build HTML delivery for primary content, metadata, canonical links, structured data, navigation, and static animation fallbacks.
9. Select `.ai/quality-profiles/web-app.yaml`, `.ai/quality-profiles/frontend-html-css.yaml`, `.ai/quality-profiles/visual-design.yaml`, `.ai/quality-profiles/animation-motion.yaml` when applicable, and `.ai/quality-profiles/seo-geo.yaml`.
10. For existing websites, complete the change-impact plan and obtain approval evidence before implementation.
11. Use `design-taste-website`, `animation-design-engineering` when applicable, and `seo-geo-website` in `implement` mode and change only the approved scope.
12. Validate source, production build or prerender output, raw HTML, headers, robots policy, sitemap, redirects, canonical/hreflang relationships, structured data, responsive composition, applicable UI states, keyboard/focus behavior, normal and reduced motion, repeated and interrupted animation, accessibility, console state, visual regression, lifecycle cleanup, and performance under representative load.
13. Complete `.ai/templates/visual-design-review.md`, `.ai/templates/ui-state-inventory.md`, `.ai/templates/animation-review.md` when applicable, and `.ai/templates/seo-geo-review.md`.
14. Report all quality gates, remaining uncertainty, deployment verification, and rollback. Do not promise design, motion, search, or AI outcomes without evidence.

`llms.txt` is optional. If used, document it as an emerging proposal, keep it limited to verified public information, and do not treat it as crawler access control or a ranking factor.
