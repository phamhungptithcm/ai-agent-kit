# Observability Rules

required_review:

* "Design changes to be observable in production through logs, metrics, traces, health checks, or audit events where appropriate."
* "Use structured logging when supported by the project's logging framework."
* "Preserve correlation identifiers, request IDs, trace IDs, span IDs, transaction IDs, job IDs, message IDs, or equivalent context across service boundaries."
* "Propagate observability context through synchronous, asynchronous, scheduled, and event-driven workflows."
* "Do not log secrets, credentials, tokens, API keys, passwords, encryption keys, session identifiers, or other authentication artifacts."
* "Do not log PII, financial data, regulated information, or sensitive business data unless explicitly approved and protected."
* "Mask, hash, redact, or tokenize sensitive values when logging is required."
* "Log significant business events, failures, retries, circuit breaker transitions, and recovery events at appropriate log levels."
* "Avoid duplicate logging across layers; log failures once at the layer responsible for handling them."
* "Include sufficient context for troubleshooting without exposing confidential information."
* "Ensure logs contain actionable context such as operation, component, outcome, duration, correlation identifier, and failure reason where applicable."
* "Avoid excessive logging on hot paths or within high-frequency loops."
* "Avoid logging entire request or response payloads unless explicitly approved."
* "Measure production-significant operations using metrics."
* "Record request counts, latency, throughput, error rates, retries, queue depth, cache performance, and resource utilization where applicable."
* "Review metric cardinality to avoid unbounded labels or high-cardinality dimensions."
* "Instrument distributed tracing for cross-service, asynchronous, or latency-sensitive workflows where supported."
* "Capture meaningful spans around external dependencies including databases, message brokers, caches, and downstream services."
* "Document how operators can verify successful deployment and runtime behavior."
* "Document expected logs, metrics, dashboards, traces, health endpoints, or validation commands for operational verification."
* "Review monitoring, dashboards, alerts, SLOs, SLIs, and runbooks when production-significant behavior changes."
* "Update alert thresholds or operational documentation when observability expectations change."
* "Document any new operational dependencies introduced by the implementation."

logging:
requirements:
- "Use structured key-value logging."
- "Use consistent field names across services."
- "Include timestamps generated by the logging framework."
- "Include correlation identifiers whenever available."
- "Log at the appropriate severity level."
- "Avoid string concatenation when structured logging is supported."

metrics:
review:
- "Request rate"
- "Success rate"
- "Failure rate"
- "Latency"
- "Retry count"
- "Timeout count"
- "Circuit breaker state"
- "Queue depth"
- "Cache hit ratio"
- "Database query duration"
- "External dependency availability"
- "Business transaction success rate"

tracing:
review:
- "Trace propagation"
- "Span relationships"
- "External service calls"
- "Database operations"
- "Messaging flows"
- "Long-running operations"
- "Background jobs"

verification:
deployment:
- "How operators verify successful deployment"
- "Expected health check behavior"
- "Expected metrics after deployment"
- "Expected log events"
- "Expected dashboard changes"
- "Expected alert behavior"
- "Rollback verification"

security:

* "Never expose sensitive information through logs, metrics, traces, exceptions, dashboards, or monitoring labels."
* "Review observability data for compliance with privacy and regulatory requirements."
* "Apply data masking before information leaves the application."

agent_constraints:

* "Do not claim monitoring, dashboards, alerts, traces, or metrics were created unless verifiable evidence exists."
* "Do not invent production dashboards, monitoring systems, or alert policies."
* "Do not remove existing observability without explicit justification."
* "Do not introduce high-cardinality labels or excessive logging without operational review."
* "Clearly distinguish implemented observability from recommended future improvements."


slo_review:
  - "Determine whether the change affects existing SLOs or SLIs."
  - "Identify customer-visible latency or availability impacts."
  - "Review error budget implications."

operational_readiness:
  - "Can an operator detect the failure?"
  - "Can an operator diagnose the root cause?"
  - "Can an operator verify successful recovery?"
  - "Can an operator distinguish transient failures from persistent failures?"

telemetry_quality:
  - "Every critical business transaction should be traceable end-to-end."
  - "Every external dependency should have latency and failure metrics."
  - "Every production incident should be diagnosable from telemetry without requiring code changes."
