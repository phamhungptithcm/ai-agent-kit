# AI Agent Kit v1.5.0 — Team Control Plane Implementation Plan

Plan ID: `AAK-TEAM-CONTROL-PLANE-V150`

Base: v1.4.0 at `c3f8557fd619ae672293e0b7f72974b04fdf5136`

Delivery branch: `hunpeolabs/v1.5.0-team-control-plane`

Roadmap: GitHub milestone 11, issues #74–#88

## Outcome

v1.5.0 turns the existing task-local team protocol into a repository-level control plane. Multiple members and agents can coordinate work across linked worktrees without silently sharing a branch, overwriting claims, accepting stale results, or treating an unverified host bridge as trusted.

The release remains local-first. It provides enforceable coordination for processes and linked worktrees that share a Git common directory, plus authenticated contracts for compatible remote host bridges. It does not claim to be a hosted distributed consensus service.

## Repository intelligence brief

Observed facts:

- `src/team-context.mjs` persists one context per task under the current worktree and prevents overlap only inside that task.
- `src/team-executor.mjs` already implements structured dispatch, heartbeat, ingest, cancellation, recovery, idempotent result transactions, and task approval checks.
- `src/execution-adapters.mjs` describes host capabilities but does not authenticate host identity or bind capabilities to signed/hashed evidence.
- `src/team-orchestrator.mjs` owns the task contract and assignment lifecycle.
- Architecture Pulse can provide post-change dependency evidence, but team conflict checks do not currently normalize symbol, API, schema, migration, or generated-artifact surfaces.
- Team benchmarks compare three modes with three repetitions and do not yet include governed shared-workspace execution or a 30-task release gate.
- Build output is generated by copying canonical `src` and `bin` into `dist`; generated skill adapters are synchronized from `.ai/skills-src`.

Gap:

- Two tasks can claim the same repository path because task-local locks and claim files do not share a repository-wide authority.
- A lease has no monotonic fencing token, so a delayed writer can return after expiry without a repository-level stale-writer proof.
- Assignment dispatch is not bound to an isolated worktree, parent snapshot, authenticated principal, or integration package.
- Integration ordering, CODEOWNER escalation, host attestation, privacy-safe SLOs, and a controlled four-mode benchmark are not first-class contracts.

## Contract spine

1. `team-control-contract`: versioned identities, capabilities, repository/task records, leases, fencing tokens, workspace bindings, integration packages, conflicts, reviews, and metrics.
2. `team-registry`: bounded atomic storage rooted in the Git common directory, optimistic revisions, lock recovery, cross-task scope admission, leases, heartbeats, release, and stale-token rejection.
3. `team-workspace`: parent snapshot validation, deterministic branch/worktree plan, safe inspection, recovery, and explicitly authorized provisioning/cleanup.
4. `team-conflicts`: normalized path, symbol, API, schema, migration, dependency, and generated-artifact surfaces with fail-closed unknown states.
5. `team-integration`: dependency-aware change queue, Integration Owner admission, reviewer independence, rollback metadata, and state transitions.
6. `team-host-bridge`: authenticated local attestation verification and capability binding; unverified bridges remain advisory or rejected.
7. `team-metrics`: privacy-safe counters, bounded event dimensions, SLO evaluation, and insufficient-evidence states.

## Implementation phases and acceptance

### Phase 0 — Contracts and identity (#74, #75)

- Add canonical JSON schemas and runtime validators.
- Require safe principal IDs, identity type, issuer, subject, roles, bounded capabilities, expiry, and evidence digest.
- Deny unknown capabilities and separate reviewer identity from author/implementer identity.
- Tests: malformed identities, expired attestations, capability escalation, secret-like fields, and backwards-compatible task-only mode.

### Phase 1 — Registry, leases, and fencing (#76, #77)

- Resolve the repository authority from `git rev-parse --git-common-dir` with a safe injected resolver for tests.
- Store one sealed registry per repository identity with atomic writes, a bounded lock, revision checks, and monotonic fencing counters.
- Admit claims across all tasks, renew with heartbeats, expire deterministically, release idempotently, and reject stale fencing tokens.
- Bind task-local claims and handoffs to the repository claim ID/token during dispatch and ingest.
- Tests: concurrent tasks, linked worktrees, lock contention, crash expiry, stolen identity, stale token, and non-overlapping parallel work.

### Phase 2 — Parent drift and isolated workspaces (#78, #79)

- Bind each assignment to parent commit, branch, worktree path, and baseline digest.
- Fail dispatch when the parent drifts or the requested workspace is shared, dirty without declaration, outside an approved root, or occupied by another active claim.
- Provide plan/inspect/provision/cleanup commands with dry-run default and explicit mutation authorization.
- Tests: same-branch writers, parent movement, dirty workspace, traversal/symlink paths, partial provisioning, recovery, and idempotent cleanup.

### Phase 3 — Integration and conflict intelligence (#80, #81)

- Create immutable change packages containing commit/baseline bindings, affected surfaces, test evidence, rollback reference, dependencies, and author identity.
- Enforce Integration Owner identity, dependency order, accepted review, fresh fencing token, and current parent before admission.
- Analyze path plus symbol/API/schema/migration/dependency/generated surfaces; unknown evidence fails closed for protected packages.
- Tests: reorder, stale packages, duplicate admission, hidden schema/migration conflicts, generated-source mismatch, rollback and resume.

### Phase 4 — Host bridge, review, and operations (#82, #83, #84)

- Verify host attestations with an explicit trust store and cryptographic digest/MAC verifier supplied by the operator; never log secret material.
- Record structured review independence and CODEOWNER escalation evidence.
- Emit privacy-safe lifecycle metrics and evaluate SLOs for claim latency, conflict detection, stale-writer rejection, integration wait, recovery, and evidence completeness.
- Tests: forged/expired/replayed attestations, self-review, missing owners, cardinality limits, incomplete windows, and redaction.

### Phase 5 — Benchmark, documentation, and assurance (#85, #86, #87)

- Compare `SINGLE_AGENT`, `UNGOVERNED_MULTI_AGENT`, `TASK_LOCAL_GOVERNED`, and `REPOSITORY_CONTROL_PLANE` modes.
- Require at least 30 comparable task cases for release-level conclusions; synthetic data remains `SYNTHETIC_ONLY`.
- Add operator, failure, recovery, migration, rollback, and release-note documentation.
- Update version to `1.5.0`, regenerate distribution and skill adapters, run full checks, packed smoke, post-build impact analysis, final implementation review, and task-completion report.

## Risk and rollback

- Registry corruption: sealed records, bounded reads, atomic rename, backup-before-migration, and deterministic recovery report.
- Lock theft: only stale locks beyond the configured limit are recoverable; recovery is recorded and never silently changes a live lease.
- Stale writers: every write-capable dispatch receives a monotonic fencing token that must still be current at ingest and integration.
- Cross-host ambiguity: reject or downgrade unverified bridges; do not market local file coordination as distributed consensus.
- Compatibility: task-local APIs remain available; repository control is opt-in for legacy callers and default for the new v1.5 CLI actions.
- Rollback: stop new admissions, export the sealed registry, allow active leases to expire or revoke them explicitly, remove only kit-owned worktrees after inspection, and return to v1.4 task-local operation.

## Verification matrix

- Contract: schema validation, unknown-field denial, version compatibility.
- Concurrency: multi-process claims, lease expiry, heartbeat races, fencing, idempotency.
- Git: branch/worktree isolation, baseline drift, dirty state, rollback.
- Integration: dependency order, structured conflicts, owner/reviewer separation.
- Security/privacy: identity forgery, replay, traversal, symlink, secret-like content, bounded storage and metrics.
- Evidence: benchmark methodology, conformance attestation, Architecture Pulse comparison, packed tarball fidelity.
- Release: `npm run check`, generated-source consistency, final implementation review, and explicit readiness blockers.
