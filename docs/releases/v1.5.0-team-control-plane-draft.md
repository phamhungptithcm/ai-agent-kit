# v1.5.0 — Repository Team Control Plane

> Release candidate trên nền `v1.4.1`. Source implementation đã được tách khỏi
> Product Content WIP, tích hợp và kiểm chứng local. Merge, tag, npm publish,
> GitHub Release và deploy chưa được phép và chưa thực hiện.

## Câu chuyện ra mắt

### Một developer giỏi có thể đi rất nhanh. Nhưng cả team chỉ đi nhanh khi không giẫm lên công việc của nhau.

Hãy hình dung một team sản phẩm ngoài đời thật.

Minh là một developer rất giỏi. Khi nhận một tính năng checkout, Minh có thể
đọc code nhanh, tìm đúng module và hoàn thành phần chính trong vài giờ. Cùng lúc
đó, Lan sửa schema đơn hàng, Nam cập nhật API, còn An chuẩn bị test và review.

Từng người đều làm tốt phần việc của mình. Rắc rối xuất hiện ở khoảng trống giữa
các phần việc.

Minh bắt đầu từ commit cũ hơn commit mà Lan đang dùng. Nam đổi một contract mà
không biết checkout cũng phụ thuộc vào nó. Hai branch cùng sửa một generated
file nhưng không ai chạm vào canonical source. Một pull request được review bởi
chính người đã viết phần quan trọng nhất. Đến lúc ghép code, team mới phát hiện
ba thay đổi đúng khi đứng riêng nhưng xung đột khi đứng cùng nhau.

Vấn đề không nằm ở năng lực của từng developer. Vấn đề nằm ở cơ chế phối hợp:
ai đang sở hữu phần việc nào, bắt đầu từ trạng thái nào, quyền tới đâu, kết quả
nào còn mới, thay đổi nào phải đi trước, và ai có quyền quyết định đưa nó vào
nhánh tích hợp.

Khi đưa coding agent vào team, khoảng trống ấy lớn hơn.

Agent có thể chạy nhanh hơn con người, mở nhiều task hơn và tạo thay đổi trong
vài phút. Nhưng nếu mỗi agent chỉ biết task của mình, hai agent ở hai task khác
nhau vẫn có thể cùng nhận một vùng code. Một agent bị timeout có thể quay lại
muộn và gửi kết quả cũ. Hai worktree có thể bắt đầu từ hai parent khác nhau.
Một host nói rằng nó hỗ trợ isolation hay cancellation nhưng chưa có bằng chứng
xác thực. “Chạy song song” lúc đó chỉ làm xung đột xảy ra nhanh hơn.

Đó là lý do có v1.5.0.

Phiên bản này đưa **Repository Team Control Plane** vào AI Agent Kit. Thay vì
chỉ điều phối bên trong một task, kit tạo một nguồn trạng thái chung cho toàn bộ
repository và các linked worktree của nó.

Mỗi member, agent và host có identity, role, capability, thời hạn và evidence
digest rõ ràng. Mỗi task đăng ký với repository. Mỗi writer làm việc trên branch
và worktree riêng, gắn với đúng parent commit. Trước khi viết, agent phải claim
không chỉ path mà cả symbol, API, schema, migration, dependency hoặc generated
surface liên quan.

Mỗi lease nhận một fencing token tăng đơn điệu. Nếu agent mất lease rồi quay
lại, token cũ không thể sống lại: result bị từ chối trước khi đi vào shared
state hay integration queue. Đây là khác biệt giữa “hy vọng agent cũ không còn
viết” và “có bằng chứng để chặn stale writer”.

Agent con không được push, merge, tag, publish hay deploy. Kết quả writer trước
hết được đóng băng bằng receipt gắn với worktree diff và evidence. Sau khi
Integration Owner tạo candidate commit theo quyền đã được duyệt, change package
phải khớp Git diff thật, parent, claim và receipt ấy. Independent Reviewer kiểm
tra đúng bộ input sẽ được admit; required owners duyệt protected surfaces bằng
identity đã xác thực. Integration Owner mới là người ký action và ghi quyết
định admission theo dependency order.

Nếu agent chạy trên host khác, v1.5.0 không mặc định tin lời khai capability.
Host bridge cần attestation có chữ ký/MAC, thời hạn và nonce chống replay. Và
local file registry chỉ được mô tả đúng với năng lực của nó: phối hợp các process
và linked worktree cùng Git common directory, không giả vờ là distributed
consensus giữa nhiều máy.

Mục tiêu của v1.5.0 không phải thay team lead hay biến mọi việc thành quy trình
nặng nề. Mục tiêu là giữ lại điều một team giỏi vẫn làm ngoài đời thật: chia
ownership rõ, bắt đầu từ cùng một thực tế, review độc lập, ghép thay đổi theo
thứ tự, và biết chính xác khi nào một kết quả không còn đáng tin.

Agent có thể nhanh. Team Control Plane giúp tốc độ ấy trở thành năng lực của cả
team, thay vì một nguồn xung đột mới.

## Release notes draft

### Highlights

- Added repository-trusted Ed25519 identities with constrained delegation,
  revocation, short-lived signed action envelopes, and durable nonce replay
  rejection. Legacy HMAC is compatibility-only degraded trust.
- Added one transactional SQLite authority under the Git common directory so
  linked worktrees atomically share tasks, claims, receipts, packages, reviews,
  decisions, trust policy, revisions, and hash-linked events.
- Added cross-task path/symbol/API/schema/migration/dependency/generated-surface
  admission, optimistic concurrency, heartbeats, monotonic fencing tokens,
  frozen writer results, and evidence-gated recovery. Lease expiry alone cannot
  authorize a conflicting writer.
- Added exact-parent and clean-worktree gates plus plan-first isolated branch
  and worktree lifecycle controls with owned cleanup markers.
- Added integration packages verified from actual Git objects, ancestry,
  changed paths, and binary diff digests; exact-input independent reviews,
  authenticated CODEOWNERS evidence, and atomic Integration Owner admission.
- Added authenticated, expiring, replay-protected host bridge attestations. An
  unavailable key remains `UNVERIFIED`; an invalid or replayed attestation is
  rejected.
- Added ledger-derived privacy-safe coordination metrics and explicit SLO
  states, including `INSUFFICIENT_EVIDENCE` when the observation window has no
  usable sample.
- Upgraded the release benchmark to four modes: single agent, ungoverned
  multi-agent, task-local governed, and repository control plane. Release-level
  conclusions require unique signed runtime receipts, at least 30 comparable
  task cases, variance, percentile, and confidence evidence.
- Added CLI operations, canonical schemas, policy, workflow, operator/recovery
  guidance, migration notes, tests, and regenerated distribution artifacts.

### Trust boundaries

- Git common-dir storage coordinates local processes and linked worktrees; it
  is not a hosted or cross-host consensus service.
- Cross-host claims require an authenticated bridge and a compatible shared
  registry backend.
- No prompt, source body, chat history, private reasoning, credential, or secret
  is permitted in durable coordination state or metrics.
- Child agents remain unable to commit, push, merge, tag, publish, deploy,
  change repository settings, or mutate production.
- Synthetic tests prove deterministic behavior, not real-world productivity or
  a world-class quality claim.

### Migration from v1.4.1

- Existing task-local orchestration remains compatible with control mode off.
- New teams can opt in with `team plan --control-plane`, an authenticated
  identity at start and lifecycle calls, and one isolated worktree per writer.
- Finish or cancel v1.4.x live claims before enabling the repository registry.
  Preview `team registry-migrate`, apply it once with backup retention, then
  require `team registry-health` to report `READY` before starting writers.
- Keep the first adoption local to one repository, review registry/queue state,
  then add verified host bridges only where a shared backend actually exists.

### Known limitations

- The default backend does not coordinate independent clones on separate
  machines.
- Admission derives changed paths and diff hashes from Git, but semantic
  reflection, dynamic wiring, and undeclared external contracts can remain
  unknown; protected surfaces therefore require current Pulse or human review.
- Worktree provisioning and cleanup require explicit apply confirmation; the
  kit does not autonomously integrate or delete developer work.
- A 30-case measured benchmark has not yet been executed in this implementation
  branch, so real-world comparative conclusions remain unavailable.
